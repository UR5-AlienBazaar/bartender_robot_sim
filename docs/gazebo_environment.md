# The Gazebo environment

The one-page record of what the simulation stack is, how to start it, and
what names and topics the rest of the system may rely on. Written for the
VLA data-collection phase (Phase 1): the scene, its three cameras, its
deterministic reset, and its ground-truth querying.

## The stack, as detected

| thing | value |
|---|---|
| ROS distribution | Humble (inside the `bartender-vla` Docker container) |
| Gazebo | Gazebo Sim **Fortress** (gz-sim 6.18.0), modern `ign gazebo` -- NOT Gazebo Classic |
| ros_gz | `ros_gz_sim`, `ros_gz_bridge` (Humble's, `ignition.msgs` wire names) |
| robot description | `bartender_description/urdf/workcell.urdf.xacro` -- ONE UR5e + Robotiq 2F-85 |
| world | `bartender_gazebo/worlds/workcell_world.sdf`, world name `workcell_world` |
| bridge launch | `bartender_gazebo/launch/sim.launch.py` (shared with the bar) |
| controllers | `workcell_controllers.yaml` via `gz_ros2_control` inside the server |
| robot spawn | `ros_gz_sim create -topic robot_description`, name `bartender_ur5e` |

Everything above `ros2_control` (MoveIt, the skills, the pendant) is
hardware-agnostic; the boundary is unchanged from before this phase.

## Bring-up: one command

```bash
# inside the container, workspace sourced:
ros2 launch bartender_bringup workcell_sim.launch.py
```

That one command starts Gazebo with the scene, spawns the UR5e, activates
`joint_state_broadcaster`, `ur_arm_controller` and `gripper_controller`,
starts MoveIt, bridges `/clock`, the three camera streams, the scene's
ground-truth pose stream, and publishes the static camera transforms.
Give it ~20 s (the controllers wait 12 s for the world, MoveIt 16 s).

Two launch arguments matter on this hardware:

- `headless:=true headless_rendering:=true` -- server only, sensors
  rendered through EGL. **On this box plain `headless:=true` without
  `headless_rendering` hangs the server** (no GLX in a headless server;
  the controller spawners then time out). With a GUI attached, plain
  default works.
- `launch_rviz:=true` for RViz (off by default for a known display bug).

**Env var, required for reliability in this container:**
`FASTDDS_BUILTIN_TRANSPORTS=UDPv4`. FastDDS's default SHM transport is
flaky in this Docker/host-network setup (service replies between
processes get lost); UDP-only fixes it. Set it in the shell that launches
the stack and in the shells that run the scripts against it. (Found the
hard way: `gz_ros2_control` waiting forever on `robot_description`,
spawners timing out on `controller_manager`.)

## Frames

| frame | what it is |
|---|---|
| `world` | the table's corner at its top surface; the URDF root |
| `base_link` | the UR5e base, at world (0.35, 0.35, 0.75), yawed -90 deg |
| `tool0` | the arm's tool frame |
| `overhead_camera_link` / `overhead_camera_optical_frame` | static, from `bartender_scene.yaml` |
| `side_camera_link` / `side_camera_optical_frame` | static, from `bartender_scene.yaml` |
| `wrist_camera_link` / `wrist_camera_optical_frame` | on the robot, `tool0 -> wrist_camera_link -> ..._optical_frame` |

Verify with:

```bash
ros2 run tf2_ros tf2_echo world overhead_camera_optical_frame
ros2 run tf2_ros tf2_echo world side_camera_optical_frame
ros2 run tf2_ros tf2_echo base_link wrist_camera_optical_frame
```

The optical frames follow the ROS convention (+z forward, +x image right,
+y image down) via a fixed `rpy(-pi/2, 0, -pi/2)` rotation from each
camera body link; the wrist camera's transform moves with the arm (it is
part of the robot description, published by `robot_state_publisher`).

## The scene and its names

Source of truth: `bartender_gazebo/config/bartender_scene.yaml`.
`scripts`-side summary (all poses in `world`, table top at z = 0.75):

| entity | model | pose |
|---|---|---|
| `bartender_table` | link of the robot description | 1.40 x 0.70 box, top at 0.75 |
| `bottle_1` | `jack_daniels_bottle` | (0.52, 0.55, 0.75) |
| `bottle_2` | `cola_bottle` | (0.68, 0.55, 0.75) |
| `bottle_3` | `debug_bottle_red` | (0.84, 0.55, 0.75) |
| `bottle_4` | `debug_bottle_green` | (1.00, 0.55, 0.75) |
| `bottle_5` | `debug_bottle_blue` | (1.16, 0.55, 0.75) |
| `glass` | `serving_glass` | (0.84, 0.30, 0.75) |

The bottle row is inside the arm's reachable band; the glass is 0.25 m
clear of bottle_3. The debug bottles are generated by
`bartender_gazebo/scripts/make_bartender_scene.py` (edit the generator,
not the SDF) and are distinct in colour AND silhouette; the colours are
debug aids, and nothing may read semantics from them.

The world SDF is GENERATED from the YAML by that same script, and
`test_bartender_scene.py` fails if either drifts, so YAML, world and
models cannot disagree. The arm's episode start is `arm_home` in the
YAML -- the SRDF's own `home` group state.

## The cameras

| camera | topic | frames | resolution |
|---|---|---|---|
| overhead | `/camera/overhead/image_raw` + `camera_info` | `overhead_camera_*` | 640x480 RGB |
| side | `/camera/side/image_raw` + `camera_info` | `side_camera_*` | 640x480 RGB |
| wrist | `/camera/wrist/image_raw` + `camera_info` | `wrist_camera_*` | 640x480 RGB |

- **Overhead**: 1.10 m above the table, straight down, 72 deg FOV. The
  bottle row runs along the top of the frame, the glass mid-frame, the
  arm's reach at the bottom. Shows which bottle is which and XY
  positions.
- **Side**: diagonal from the table's near side (y = -0.35, z = 1.30),
  aimed at the bottle row and glass. Shows bottle elevation, tilt, pour
  height -- the depth information the overhead view lacks. Off-axis so
  the arm's base does not occlude the workspace.
- **Wrist**: 8 cm off the tool axis, 10 cm beyond the flange, looking
  along the gripper approach. Shows fine approach, grasp alignment and
  the glass rim during a pour.

Images carry simulation timestamps (`use_sim_time` throughout; `/clock`
is bridged). No depth, no segmentation, no point clouds, no liquid --
deliberately, for this phase.

**Rate on this hardware**: the cameras are configured at 10 Hz (the YAML
`fps` knob). This dev box renders on CPU (llvmpipe; the host is a VM
without `/dev/dri`), and three 640x480 streams at the 30 Hz target hold
the whole simulation at RTF ~0.2 -- at 10 Hz it runs at ~0.4-0.5. On GPU
hardware, raise `fps` back to 30 in `bartender_scene.yaml`, re-run
`make_bartender_scene.py`, and rebuild. The measured rate is part of
`scripts/validate_cameras.py`'s output.

## Reset

```bash
python3 scripts/reset_bartender_scene.py --once    # one reset, then exit
python3 scripts/reset_bartender_scene.py           # serves /reset_bartender_scene (std_srvs/Trigger)
```

A reset (1) drives the arm to `arm_home` through the trajectory
controller (honest motion, tolerance-checked), (2) removes and re-creates
every object at its nominal pose (a fresh entity has exactly zero
velocity; a teleport would keep it), and (3) reads the poses back and
reports the worst residual in mm. Verified 10/10 consecutive resets,
each preceded by a fresh disturbance, residual 0.0 mm every time.

The service exists for the future episode runner; call it between
episodes. Startup leaves the arm at its spawn pose (all joints zero --
the arm hangs off the table's near edge there), so the first reset also
moves the arm to home; every episode thereafter starts from home.

## Ground truth

```bash
python3 scripts/scene_state.py            # poses of bottle_1..5, glass
```

Reads SceneBroadcaster's `/world/workcell_world/dynamic_pose/info`
(bridged to ROS, the same stream the bar's skills use). Entities are
queried by name; a missing entity is reported, never skipped. The future
reward system reads these poses (plus the glass geometry in the YAML:
radius 0.04, height 0.09, opening plane at z = 0.84).

## The scripts

| script | what it does |
|---|---|
| `scripts/scene_state.py` | ground-truth poses; `--watch` streams |
| `scripts/reset_bartender_scene.py` | reset (CLI or `/reset_bartender_scene`) |
| `scripts/validate_cameras.py` | captures one frame per camera to `artifacts/camera_validation/`, prints resolution/encoding/stamp/frame_id, measures Hz |
| `scripts/check_bartender_env.py` | readiness check: joint states, controller, all six camera topics, all six entities; nonzero exit if anything is missing |
| `scripts/view_cameras.py` | three-pane debug view (overhead | side / wrist) -- debugging only, NOT a policy input |

All of them need the workspace sourced (and the UDPv4 env var).

## Known gaps, on purpose or not

- **The arm does not collide with the table in Gazebo** (both are links
  of one spawned model). Pre-existing workcell behaviour, not a
  regression: MoveIt still refuses to plan into the table, which is what
  actually guards the real robot. Verified that world objects DO collide
  with the table (a probe bottle rests on it), so bottles and glass are
  unaffected.
- The ros2 CLI in this container is unreliable (its daemon wedges);
  prefer the rclpy scripts.
- Entity ids churn across resets (remove + create); query by name.
